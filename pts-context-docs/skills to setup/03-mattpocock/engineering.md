# Matt Pocock — Engineering (17)

O núcleo de engenharia: alinhamento, especificação, execução, revisão e manutenção de design. Divididas em user-invoked (orquestração, `/comando`) e model-invoked (disciplina reutilizável, automática).

## Invocação

- **User-invoked** (`disable-model-invocation: true`): `ask-matt`, `grill-with-docs`, `triage`, `improve-codebase-architecture`, `setup-matt-pocock-skills`, `to-spec`, `to-tickets`, `implement`, `wayfinder`
- **Model-invoked**: `prototype`, `diagnosing-bugs`, `research`, `tdd`, `domain-modeling`, `codebase-design`, `code-review`, `resolving-merge-conflicts`

---

## ask-matt

- **O que faz**: router — diz qual skill ou fluxo se aplica à sua situação. Mapeia o fluxo principal (grill → spec → tickets → implement → review) e as on-ramps.
- **Como invocar**: digite "ask matt" ou descreva a situação sem saber a skill.
- **Quando usar**: não sabe qual skill usar; sempre que for começar trabalho de engenharia.
- **Quando NÃO usar**: você já sabe a skill exata.
- **Exemplo**: "tenho um codebase e uma ideia" → aponta para `/grill-with-docs` → `/to-spec` → `/to-tickets` → `/implement`.

## grill-with-docs

- **O que faz**: sessão de grilling (entrevista implacável, uma pergunta por vez, resposta recomendada) que **também** constrói o domain model: cria/atualiza `CONTEXT.md` e ADRs inline via `domain-modeling`.
- **Como invocar**: `/grill-with-docs` — tem codebase.
- **Quando usar**: você tem código e ideia vaga; quer alinhar E deixar paper trail.
- **Quando NÃO usar**: sem codebase (use `/grill-me`); sem tempo de entrevista (use `to-spec` que não entrevista).
- **Exemplo**: "quero adicionar materialização de lições no course-video-manager" → entrevista gera `CONTEXT.md` com termo "materialization cascade" e ADR.

## to-spec

- **O que faz**: transforma a conversa atual em spec (PRD técnico) e publica no issue tracker. **Não entrevista** — sintetiza o que já foi discutido. Identifica seams de teste (ideal: um só) e confirma com usuário.
- **Como invocar**: `/to-spec`.
- **Quando usar**: decisões já tomadas; quer congelar em documento antes de ticketar.
- **Quando NÃO usar**: ideia ainda vaga (grille antes); sem issue tracker configurado (rode `/setup-matt-pocock-skills`).
- **Exemplo**: conversa sobre nova feature → spec com Problem Statement, Solution, seams, publicado com label `ready-for-agent`.

## to-tickets

- **O que faz**: quebra spec/plano/conversa em **tracer-bullet tickets** (vertical slices), cada um declarando seus **blocking edges**. Local = 1 arquivo por ticket em `.scratch/<feature>/issues/`; real tracker = links de bloqueio nativos.
- **Como invocar**: `/to-tickets`.
- **Quando usar**: spec pronta; trabalho multi-sessão ou delegável.
- **Quando NÃO usar**: trabalho de um contexto só (vá direto ao `implement`).
- **Exemplo**: spec → 5 tickets verticais com edges de bloqueio; "make the change easy, then make the easy change" (prefactor).

## implement

- **O que faz**: implementa o trabalho descrito no spec/tickets. Usa `/tdd` em seams pré-acordados, roda typecheck/tests regularmente, fecha com `/code-review`, commita.
- **Como invocar**: `/implement`.
- **Quando usar**: ticket/spec pronto para build.
- **Quando NÃO usar**: sem spec/ticket claro (grille/to-spec antes).
- **Exemplo**: pega ticket do `to-tickets` → slices de TDD → review → commit.

## triage

- **O que faz**: move issues/PRs externos por uma state machine de papéis de triagem (bug/enhancement, verify, grill se preciso, agente-ready briefs). PR = issue com código anexado. Todo comentário gerado tem disclaimer "generated by AI during triage".
- **Como invocar**: `/triage`.
- **Quando usar**: triar issues novas, preparar briefs prontos para agente.
- **Quando NÃO usar**: você é o único autor do repo e não recebe issues.
- **Exemplo**: issue `#42` → categoriza, verifica repro, escreve AGENT-BRIEF.md com label.

## wayfinder

- **O que faz**: planeja trabalho **grande demais para uma sessão** como um mapa compartilhado de **decision tickets** no issue tracker (issue `wayfinder:map` + filhos). Resolve tickets um a um até a rota ficar clara. Planeja, não executa — salvo override nas Notes.
- **Como invocar**: `/wayfinder`.
- **Quando usar**: ideia grande com fog; destino incerto; trabalho que exige várias decisões.
- **Quando NÃO usar**: caminho já claro (vai direto a spec/tickets).
- **Exemplo**: "migrar o banco inteiro para event-sourcing" → mapa de decision tickets (formato de evento, migração de dados, replay...) resolvidos um a um.

## prototype

- **O que faz**: código descartável que responde a uma pergunta de design. Dois ramos: **LOGIC** (app de terminal interativo para testar state model/lógica) e **UI** (várias variações radicais de UI numa rota só, trocáveis por search param). Regras: throwaway marcado, 1 comando para rodar, sem persistência, sem polish, superfície o estado.
- **Como invocar**: automático — "prototipe", "será que esse state model funciona?".
- **Quando usar**: pergunta de design que precisa de resposta runnable (lógica, UI que precisa ver).
- **Quando NÃO usar**: resposta definitiva em produção (prototype é descartável); pergunta que a conversa resolve.
- **Exemplo**: validar máquina de estados do fluxo de metas do PTS → app de terminal que empurra o state machine por casos difíceis.

## diagnosing-bugs

- **O que faz**: loop de diagnóstico para bugs difíceis e regressões. **Fase 1 é a skill**: construir um feedback loop tight (teste falho, curl, script headless, replay de trace, harness, fuzzing, bisection, differential) — se o loop fica vermelho só nesse bug, achar a causa é mecânico. Depois: reproduzir → minimizar → hipótese → instrumentar → fix → teste de regressão.
- **Como invocar**: automático — "diagnostique", "debug isso", "está lento/quebrado".
- **Quando usar**: bug difícil, regressão de performance, comportamento estranho.
- **Quando NÃO usar**: bug trivial com causa óbvia (skill é overkill).
- **Exemplo**: bug intermitente de checkout → feedback loop tight (harness com payload real replay) → bisection → fix.

## research

- **O que faz**: dispara **agente em background** para investigar questão contra **fontes primárias** (docs oficiais, código-fonte, specs) e salvar achados em arquivo Markdown com citações.
- **Como invocar**: automático — "pesquise X", "documente a API".
- **Quando usar**: leitura de docs/legwork delegável enquanto você segue trabalhando.
- **Quando NÃO usar**: decisão rápida que já se sabe; pesquisa que exige acesso não-automático.
- **Exemplo**: "documente o fluxo FHIR do e-SUS PEC" → agente lê docs oficiais e salva `notes/fhir-esus.md` citando cada claim.

## tdd

- **O que faz**: TDD red→green. Define o que é teste bom (verifica comportamento via interface pública, lê como spec), **seams** (testar só em seams pré-acordados e confirmados), anti-patterns (implementation-coupled, tautological, horizontal slicing), regras do loop (red antes de green, um slice por vez, refactor fora do loop).
- **Como invocar**: automático — "test-first", "red-green-refactor", "integração".
- **Quando usar**: construir feature/fix bug test-first; qualquer slice vertical.
- **Quando NÃO usar**: protótipo descartável (sem testes, ver `prototype`).
- **Exemplo**: feature "checkout com carrinho válido" → acordo seams → teste falha → código mínimo → refactor na review.
- **Arquivos de apoio**: `tests.md` (exemplos), `mocking.md` (diretrizes de mock).

## domain-modeling

- **O que faz**: disciplina **ativa** de modelagem: desafia termos, inventa cenários edge, escreve glossário (`CONTEXT.md`) e decisões (`docs/adr/`) no momento em que cristalizam. Suporta múltiplos contexts via `CONTEXT-MAP.md`.
- **Como invocar**: automático — quando o modelo de domínio está mudando, não só consumido.
- **Quando usar**: definir/hardene termo, registrar decisão de arquitetura; durante `grill-with-docs`.
- **Quando NÃO usar**: só ler o vocabulário para outra tarefa (isso é hábito de uma linha, não essa skill).
- **Exemplo**: surgiu termo "materialização" na conversa → grava no `CONTEXT.md` + ADR da decisão.

## codebase-design

- **O que faz**: vocabulário compartilhado para desenhar **deep modules** (muita comportamento atrás de interface pequena, em seam limpo, testável pela interface). Glossário preciso: module, interface, implementation, depth, seam, adapter, leverage, locality. "Delete a test" — se deletar não concentra complexidade, era shallow.
- **Como invocar**: automático — desenhar/melhorar interface de módulo, achar seams, tornar código testável/navegável.
- **Quando usar**: qualquer design/restruturação de código; quando outra skill precisa do vocabulário.
- **Quando NÃO usar**: projeto sem foco em design (mas a skill recomenda usar sempre que código for desenhado).
- **Exemplo**: módulo `auth` com 20 funções públicas superficiais → aprofundar para interface pequena, seam em cima, callers exercitam mais comportamento por unidade de interface.

## code-review

- **O que faz**: review de duas eixos do diff desde um ponto fixo (commit, branch, tag, merge-base): **Standards** (segue as coding standards do repo + Fowler smell baseline) e **Spec** (implementa fielmente o issue/PRD origem). Roda em **subagentes paralelos** para não poluir contexto, agrega findings lado a lado.
- **Como invocar**: automático — "revise a PR", "review desde X".
- **Quando usar**: revisar branch/PR/WIP; antes de merge.
- **Quando NÃO usar**: sem ponto fixo/spec (skill pede); diff trivial.
- **Exemplo**: `git diff main...HEAD` → dois subagentes (Standards/Spec) → relatório lado a lado.

## resolving-merge-conflicts

- **O que faz**: resolve conflito de merge/rebase hunk por hunk, por intenção rastreada até a fonte primária de cada lado (commits, PRs, issues). Preserva ambas intenções quando possível; nunca `--abort`; roda checks (typecheck/tests/format) e termina a operação.
- **Como invocar**: automático — quando merge/rebase conflita.
- **Quando usar**: conflito em progresso.
- **Quando NÃO usar**: nada conflitando.
- **Exemplo**: conflito em `auth.ts` → lê commits dos dois lados → resolve preservando intenções → `git add` + commit.

## improve-codebase-architecture

- **O que faz**: escaneia codebase por oportunidades de **deepening** (refactors que transformam módulos shallow em deep), apresenta como relatório HTML visual, e grilla sobre o que você escolher. Usa vocabulário de `codebase-design` + domínio de `CONTEXT.md`; respeita ADRs.
- **Como invocar**: `/improve-codebase-architecture`.
- **Quando usar**: resgatar codebase virou ball of mud; rodar a cada poucos dias em codebase ativo.
- **Quando NÃO usar**: codebase saudável/pequeno (YAGNI).
- **Exemplo**: scan via Explore → hot spots por `git log` → relatório de oportunidades → grilla sobre "aprofundar módulo X".

## setup-matt-pocock-skills

- **O que faz**: scaffolding por-repo da config que as skills assumem: issue tracker (GitHub por padrão, local markdown suportado), labels de triagem (5 papéis canônicos), layout de domain docs (`CONTEXT.md`, ADRs) + seção `## Agent skills` no `AGENTS.md`/`CLAUDE.md`.
- **Como invocar**: `/setup-matt-pocock-skills` — **uma vez por repo**, antes das outras skills de engenharia.
- **Quando usar**: repo novo; instalar skills.
- **Quando NÃO usar**: config já feita.
- **Exemplo**: repo novo → escolhe GitHub como tracker, define labels (`bug`, `enhancement`, `ready-for-agent`...), cria `docs/agents/issue-tracker.md`.

## Limitações do grupo

- **Presumem issue tracker configurado** — sem `/setup-matt-pocock-skills`, várias skills falham no primeiro passo.
- **Dependem de `CONTEXT.md` e ADRs** para qualidade — sem domínio documentado, vocab degrada.
- **Overlap com Superpowers** (TDD, review, plans) — escolha um fluxo; misturar gera instruções conflitantes.
- **Algumas skills são opinadas** (deep modules, tracer bullets) — podem ir contra convenções existentes do seu projeto.
