## Issue #2 — Portas canônicas + adapters

Estrutura em `src/server/integrations/`:

- `contract.ts`: portas `BaselineSource.getBaseline(paciente) → BaselinePaciente` e `OutboundGateway.enviarMarcacao/enviarReferencia/enviarEvento → DeliveryReceipt`. Tipos canônicos, zero acoplamento com e-SUS/RNDS.
- `canonical/`: modelos internos (`BaselinePaciente`, `MarcacaoPTS`, `ReferenciaPTS`).
- `format/`: tradutores puros canônico↔FHIR R4 (mínimo), canônico↔XML (mínimo), canônico↔JSON.
- `sources/mock.ts`: mock determinístico por CPF/CNS conhecidos (tabela fixa no código).
- `outbound/mock.ts`: mock que devolve `DeliveryReceipt` com id/status.
- Base da fila outbound (ADR-0006): função que enfileira evento canônico; worker real é Fase 2.

**Aceite**: núcleo clínico só importaria `contract.ts`/`canonical/`; mock determinístico; round-trip testado para FHIR R4 e XML (canônico → formato → canônico = igual); `enviar*` retorna receipt.

**Decisões automáticas**:
- XML mínimo: serialização própria com template strings + parse com regex/DOM leve — NÃO adicione dependência nova (ladder: stdlib primeiro). Round-trip cobre os campos do modelo canônico apenas.
- FHIR R4 mínimo: Patient/Condition/MedicationStatement mapeados para `BaselinePaciente`.
- Mock determinístico: CPFs de teste fixados em constante exportada (ex.: `52998224725` → baseline completa; `11144477735` → baseline parcial) — reutilize esses CPFs no seed/e2e de #23.
