## 1. Resumo executivo

**A aplicação sobe e o núcleo funciona.** `docker compose up db mailhog` + `db:deploy`
+ `db:seed` + `pnpm dev` → `/api/health` responde `{"status":"ok","db":"up"}`. Login,
RBAC por rota, painel do caso, recepção, triagem, metas, mural, SOAP e avaliação
Fisio/TO renderizam e persistem. `pnpm typecheck && pnpm lint && pnpm test` → **limpo,
234 testes / 28 arquivos** (com Postgres no ar).

**As 17 issues estão substancialmente entregues** — não há "DONE fantasma" grosseiro.
As 5 funções puras exigidas por TDD existem, testadas com casos de borda
(`calcularSemaforo`, `elegibilidadePorEscopo`, `calcularDivergencia`, `semaforoDeReuniao`,
`verificarConflitoMetas`) + `marcarCif`. Auditoria append-only same-tx e lock otimista
(409) estão implementados de forma consistente nos usecases de mutação.

**O que falta para a Fase 1 MVP (`plano/07`: M1, M2, M3, M5 + M4 Fisio/TO):**

| Módulo | Estado |

## 7. Findings priorizados (intent vs. implementado)

### [ALTO] PTS `FECHADO` não é somente-leitura no servidor

- **Intenção:** `plano/13` §10 "PTS `FECHADO` → somente leitura para a equipe"; `CONTEXT.md`
  "Acesso em modo histórico: PTS fechado vira somente leitura"; `Perguntas/03` §4; issue #16
  aceite "PTS FECHADO → banner somente-leitura".
- **Realidade:** só `registrarEvento` (`care-plan/eventos.ts`) recusa PTS fechado. `criarMeta`
  e `mudarStatusMeta` (`care-plan/metas.ts`), `comentarMural` (`care-plan/mural.ts`),
  `criarAvaliacaoSoap` (`clinical/soap.ts`), `criarAvaliacaoEspecialidade`
  (`clinical/avaliacao-especialidade.ts`) **não checam status** — gravam em PTS encerrado. O
  painel (`app/casos/[ptsId]/page.tsx`) mostra o banner e passa `podeEscrever` só pela
  permissão, não pelo status, então os formulários continuam visíveis.
- **Impacto:** qualquer membro da equipe com permissão de escrita adiciona avaliação/meta/
  comentário a um caso que já teve alta — registro clinicamente inconsistente, fura a regra
  de trilha histórica íntegra.
- **Correção (enxuta):** um guard compartilhado `assertPtsMutavel(ptsId, tx)` chamado dentro
  da transação nos 5 usecases de escrita (~5 call sites, 1 helper). `grep -rn "FECHADO"
  src/server` hoje só acha `eventos.ts` e `maquina-status.ts`.

### [ALTO] Sessão JWT é snapshot estático — bloqueio/mudança de papel só vale no próximo login

- **Intenção:** `plano/17` §4 "Login bloqueado se `PENDENTE`/`BLOQUEADO`"; guardrail
  "Mudança de papel/permissão grava auditoria" (implica efeito).
- **Realidade:** `lib/auth.ts` — o callback `jwt` só copia `papelId/status/...` para o token
  no sign-in inicial (`if (user)`); nunca relê o banco. `authorize` só checa `status ===
  "ATIVO"` no momento do login. Um usuário logado que for `BLOQUEADO` ou trocar de papel
  mantém a sessão antiga até o token expirar (30 dias — `session().expires`).
- **Impacto:** revogar acesso não tem efeito imediato; downgrade de permissão idem. Em
  contexto LGPD/clínico, "desligar acesso" precisa ser imediato.
- **Correção:** revalidar `status`/`papelId` contra o banco no callback `jwt` (com pequeno
  TTL de cache), ou checar `status` em `requireAuth()`.

### [MÉDIO] Dashboard visão GESTÃO sem filtro de CER

- **Intenção:** `plano/13` §10 "Gestor: … todos os PTS **do CER** (visão agregada)";
  `Perguntas/03` §3.6 "Escopo: todos os PTS do CER".
- **Realidade:** `care-plan/dashboard.ts:78-79` — branch `GESTAO` faz
  `db.pts.groupBy({ by: ["status"] })` e `by: ["semaforoReuniao"]` **sem `where: { cerId }`**.
  As branches `CLINICA` e `RECEPCAO_TRIAGEM` filtram por CER; só a de gestor não.
- **Impacto:** num deploy com >1 CER, o gestor vê agregados de todos. Mitigado hoje por
  deploy-per-org (ADR-0010) + seed com 1 CER, mas o schema é multi-CER e o `Pts` tem
  `@@index([cerId, status])` justamente para esse filtro.
- **Correção:** `where: { cerId: usuario.cerId ?? undefined }` nos dois `groupBy`.

### [MÉDIO] `atribuirPapelUsuario` protegido por permissão de leitura

- **Intenção:** `plano/17` §4 "`papeis.gerenciar`, `config.*`, `usuarios.aprovar` somente
  para base `ADMIN`"; trocar o papel de um usuário = mexer nas permissões dele.
- **Realidade:** `iam/papeis.ts:270` — `atribuirPapelUsuario` chama
  `requirePermissao("admin.usuarios.ver")`. Uma permissão de **listar** usuários habilita
  **reatribuir papéis**.
- **Impacto:** escalonamento de privilégio se algum papel ganhar `admin.usuarios.ver` sem
  `admin.papeis.gerenciar`. Hoje só o papel ADMIN tem os dois no seed, então não explora na
  prática — mas o guard está errado.
- **Correção:** trocar para `admin.papeis.gerenciar` (ou exigir as duas).

### [MÉDIO] Guardrail "GESTOR sem recurso clínico" cobre só o prefixo `clinical.`

- **Intenção:** ADR-0009 / `plano/17` §4 "Papel base `GESTOR` nunca ganha recurso clínico";
  `Perguntas/03` §3.6 gestor = "**leitura apenas** de dados clínicos individualizados".
- **Realidade:** `iam/permissoes.ts:3` — `RECURSOS_CLINICOS = ["clinical."]`. `validarRecursos`
  só barra `clinical.*` para base GESTOR. `care-plan.meta.escrever`, `care-plan.mural.escrever`,
  `care-plan.pts.encerrar`, `triage.triagem.escrever`, `triage.semaforo.ajustar` **passam**.
- **Impacto:** o admin da org pode criar um papel base GESTOR que escreve metas, encerra PTS
  ou preenche triagem — contraria a separação gestão×clínica. (O seed já dá
  `triage.semaforo.ajustar` ao papel GESTOR — provavelmente intencional para regulação, mas
  ilustra que o guardrail não pega.)
- **Correção:** ampliar `RECURSOS_CLINICOS` para `["clinical.", "care-plan.meta", "care-plan.pts",
  "care-plan.mural", "triage.triagem", "triage.semaforo"]` — ou definir a lista explícita de
  recursos "clínicos" e validar contra ela. Ajustar o seed do papel GESTOR em conjunto.

### [MÉDIO] Fila outbound / notificação loop-fechado / contrarreferência ausentes

- **Intenção:** ADR-0006 (tabela `outbound_queue` + INSERT same-tx); PRD M1 "Notificação em
  loop fechado: e-mail/SMS à eSF + Marcador de PTS Ativo no e-SUS PEC"; PRD M2 +
  roadmap Fase 1 "M2 — Triagem: semáforo + **contrarreferência**".
- **Realidade:** `integrations/outbound/fila.ts` é uma fila **em memória** (`criarFilaMemoria`),
  não referenciada por nenhuma mutação. Nenhuma tabela. `OutboundGateway` só tem o mock.
  Recurso `triage.contrarreferencia.emissao` no seed sem nenhum usecase.
- **Impacto:** a eSF não é avisada; não há guia de contrarreferência; o PTS não fica visível
  no e-SUS. São dores centrais do PRD (M1/M2) e critério de aceite de fase.
- **Correção:** fora do escopo de "fix rápido" — é feature. Mínimo p/ destravar: tabela
  `outbound_event` + enfileirar no `abrirPts`/encerramento; worker fica Fase 2.

### [MÉDIO] Ciclo de vida do PTS e reavaliação sem UI

- **Intenção:** `CONTEXT.md` máquina de estados `EM_AVALIACAO → PACTACAO → SEGUIMENTO →
  REAVALIACAO → …`; UC-11 (versionar), UC-12 (encerrar), RF-UX-12 (comparativo).
- **Realidade:** `transicionarStatusPts` e `atualizarSemaforoReuniao` (`care-plan/`) estão
  implementados e testados mas **não há chamada em `src/app`** (`grep` confirma "NONE in UI").
  `PtsRevisao` nunca é criado.
- **Impacto:** pela aplicação, todo PTS fica preso em `EM_AVALIACAO`; não há pactuação
  formal, encerramento, nem "o que mudou".
- **Correção:** wire — botões de transição no header do painel (permissão
  `care-plan.pts.revisar`/`.encerrar`), form de encerramento. Feature pequena, backend pronto.

### [BAIXO] Leituras de paciente sem escopo de CER

- **Realidade:** `reception/paciente.ts` — `buscarPacientePorDocumento` e `buscarDuplicidade`
  não filtram por `user.cerId`. `consentimento.ts` e `cuidador.ts` **checam** CER; a busca de
  paciente não.
- **Impacto:** leitura cross-CER se multi-instância. Mitigado por deploy-per-org.
- **Correção:** adicionar `cerId: user.cerId` ao `where`.

### [BAIXO] Re-triagem: lock otimista opcional

- **Intenção:** issue #18 aceite "versão velha → 409".
- **Realidade:** `triage/registrar.ts` — `version` é `.optional()` no zod da re-triagem; se
  o cliente omitir, `updateMany where: { versao: undefined }` ignora o filtro → sem 409.
- **Correção:** tornar `version` obrigatório quando `ptsId` presente (`.refine`).

### [BAIXO] Nascimento do PTS não é atômico com a triagem

- **Intenção:** issue #18 "transação: `abrirPts` + persiste `triagem` + auditoria".
- **Realidade:** `triage/registrar.ts:110` (ponytail assumido) — `abrirPts` roda em transação
  própria, depois abre-se outra para a triagem. Falha no meio deixa PTS órfão sem triagem
  (recuperável via re-triagem).
- **Correção:** aceitar como ponytail documentado, ou refatorar `abrirPts` para receber um
  `tx` opcional.

### [BAIXO] SOAP sem escalas com score automático

- **Intenção:** PRD M3 "escalas clínicas com score automático — Ashworth, Glasgow (O)".
- **Realidade:** `soap-schema.ts` — S/O/A texto livre + grade de serviços; as escalas 0–100 de
  `relato`/`avaliacaoClinica` existem só para a divergência saudável, não para score clínico.
- **Correção:** feature — adicionar escalas estruturadas ao payload `O`.

### [BAIXO] Consistência de `versao` entre SOAP e especialidade

- `avaliacao-especialidade.ts:111` faz `tx.pts.update({ data: { versao: { increment: 1 } } })`;
  `soap.ts` não. Decidir se avaliação bumpa a versão do PTS e uniformizar.
