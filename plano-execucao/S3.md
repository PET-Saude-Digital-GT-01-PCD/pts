## Issue #19 — Cuidador (Zarit) + consentimento LGPD

- Server action `registrarCuidador` (zod): pacienteId, nome, parentesco, idade, comorbidadesJson, zaritScore (0–24), vulnerabilidadesJson. Permissão: `recepcao.paciente.cadastrar`.
- **Decisão automática**: Zarit "alto" = `zaritScore >= 12` (constante nomeada `ZARIT_ALTO`). Alto → alerta visível ao Serviço Social no cadastro (banner/selo; notificação real é Fase 2).
- Server action `registrarConsentimento` (zod): pacienteId, termoVersao, canal (TABLET/WHATSAPP/GOVBR), assinaturaRef (placeholder string ok — `ponytail:`). Permissão: `recepcao.consentimento.registrar`.
- Consentimento **append-only**: revogação = novo registro com `revogadoEm` preenchido. Nunca update/delete. Histórico sempre preservado.
- Auditoria same-tx nas duas actions.
- Tela: seções "Cuidador" e "Consentimento" em `/recepcao/novo` (após o bloco do paciente).

**Aceite**: cuidador salvo FK RESTRICT; Zarit alto alerta visível; consentimento com canal+versão; revogação preserva histórico; auditoria.

## Issue #18 — Persistência da triagem + nascimento do PTS

Depende dos merges de #4 e #14 (funções puras da S4 em `src/server/triage/`) e #13 (`abrirPts` da S2). Polling do RUNBOOK. **Não reimplemente as funções puras — importe-as.**

Server action `criarTriagem` (`src/server/triage/registrar.ts`), fluxo:

1. Input zod: pacienteId OU ptsId (re-triagem); eixosJson (clínico/bandeiras, funcional 4 sliders 0–100, social); motivo.
2. Compute ANTES da transação (funções puras): `calcularSemaforo(...)` (#4) e `elegibilidadePorEscopo(cid, motivo, escoposCER)` (#14) — escopos vêm do CER do usuário.
3. **Nascimento (sem ptsId)**:
   - `ELEGIVEL` → transação: `abrirPts` + persiste `triagem` (ptsId novo) + auditoria.
   - `REVISAO_MANUAL` → tratada como elegível-com-decisão-clínica: nasce PTS + triagem com `resultadoElegibilidade=REVISAO_MANUAL` exigindo `justificativa` do triador (zod recusa sem justificativa) + auditoria. *(Decisão automática: schema exige `triagem.ptsId NOT NULL`; registrar-sem-PTS é impossível hoje — contrarreferência plena fica pra Fase 2, conforme a própria issue.)*
   - `NAO_ELEGIVEL` → **não persiste nada**; UI mostra justificativa padrão + orientação de retorno à APS.
4. **Re-triagem (com ptsId)**: persiste sempre na mesma transação, lock otimista (`versao` → 409).
5. Ajuste manual: action dedicada grava `AjusteClassificacao` append-only (`de`, `para`, `motivo` obrigatório — sem motivo recusa) + auditoria same-tx. Classificação vigente = ajuste mais recente. Permissão `triage.semaforo.ajustar`; preencher triagem exige `triage.triagem.escrever`.
6. Tela aba **Triagem** no painel `/casos/[ptsId]#triagem` (shell criado pela S2 na #16): form 3 eixos (sliders!), resultado do semáforo com `ui/semaforo.tsx`, botão ajustar (justificativa obrigatória).

**Aceite**: triagem concluída → PTS criado e visível; ajuste sem motivo recusado; pontuacaoJson reproduz mesmo input; versão velha → 409; tela mostra semáforo.

**Fallback se #16 ainda não mergeou após os dois ciclos de polling**: construa a tela como página autônoma `/pacientes/[pacienteId]/triagem` e deixe nota no status para integração posterior na aba. Não bloqueie a entrega das actions/testes.
